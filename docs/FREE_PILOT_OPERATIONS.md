# Piloto sin worker contratado

Decisión del 27/09/2026: conservar Supabase Free con **copia manual cifrada** y no contratar Render por ahora. El procesamiento de materiales v2 puede ejecutarse en una computadora operada por el titular; el worker solo inicia conexiones salientes a Supabase y no necesita un puerto público.

## Worker local

1. Completar primero la copia de base y objetos y la migración coordinada de [COORDINATED_RELEASE.md](./COORDINATED_RELEASE.md). La migración v2 desactiva el consumidor anterior; no se ejecuta sola.
2. Instalar las dependencias con `pnpm install`. Con la CLI de Supabase ya autenticada y vinculada al proyecto correcto, el modo `--linked` lee la clave de servicio en memoria y no crea un `.env`: ejecutar `node scripts/worker-local.mjs --linked`. Alternativamente se pueden guardar `SUPABASE_URL` y `SUPABASE_SERVICE_ROLE_KEY` en `.env` en la raíz o `apps/worker/.env`, ambos ignorados por Git, y ejecutar `pnpm worker:local`. **No pegar la clave en chat, tickets, repositorio o variables públicas**. La IA es opcional: sin proveedor, se extrae el texto nativo y se conserva el original, pero OCR e indexación no se completan.
3. El lanzador consulta el contrato remoto `20260927020000` y rechaza un segundo worker con latido vigente. Si el esquema no está listo o faltan credenciales, sale sin consumir trabajos. La terminal debe seguir abierta y la computadora debe mantenerse encendida, conectada y sin suspensión. El preflight remoto también puede leer la clave en memoria: `node scripts/release-preflight.mjs --remote --linked`.
4. Comprobar en el panel de operaciones el latido `materials`, `pipeline_version = 2`, estado `idle` o `processing` y ausencia de alertas. `pnpm release:preflight:remote` comprueba esas condiciones antes de publicar el cliente. Detener con Ctrl+C y verificar que el latido caduque; una tarea interrumpida se recupera por lease/reintento.

Una PC apagada o desconectada deja los materiales en espera. El procesamiento reanuda al volver a arrancar; esta modalidad sirve para **pruebas controladas**, pero no aprueba el gate de operación G8 ni ofrece disponibilidad de producción. Para alumnos reales se deben comprobar seguridad del equipo, continuidad operativa, restauración y tiempo de atención. El service role permite acceso amplio y exige cuenta local protegida, disco cifrado y no sincronizar `.env` con servicios personales.

Render no ofrece background workers en Free. Una web Free que duerme, una función corta o un cron eventual no sustituye sin rediseño el worker actual, que admite trabajo de hasta 20 minutos por claim y librerías nativas para documentos. [Render Free](https://render.com/docs/free), [límites de Supabase Edge Functions](https://supabase.com/docs/guides/functions/limits), [límites de Cloudflare Workers](https://developers.cloudflare.com/workers/platform/limits/).

## Copia manual cifrada en Supabase Free

La copia elegida comprende **dos conjuntos separados**: roles/esquema/datos PostgreSQL y bytes de los objetos del bucket privado `materials`. Un dump de la base solo contiene los metadatos de Storage, no los archivos. El script `scripts/backup-supabase-free.mjs` toma cinco dumps (incluida la historia de migraciones), lista Storage y cifra cada flujo con AES-256-GCM mientras se lee. No genera dumps SQL ni originales legibles en disco. Verifica el descifrado y el hash de cada pieza, deja nombres de objetos solo en `manifest.json.enc` y crea `COMPLETE.json` únicamente al terminar. La CLI requiere Docker Desktop en ejecución y puede pedir la contraseña de la base. [Backup y restore con CLI](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore), [alcance de los backups](https://supabase.com/docs/guides/platform/backups).

Ejecutar desde una terminal interactiva, con la CLI oficial instalada y el proyecto correcto vinculado:

```powershell
node scripts/backup-supabase-free.mjs --dest 'C:\Users\tavan\Documents\Codex\KusiyBackups\FECHA-UNICA' --project-ref oaravhmdvcwcvjnyweig
```

El directorio de destino debe ser nuevo y estar fuera del repositorio. La frase de cifrado se solicita dos veces; la consola muestra asteriscos, no los caracteres. No se pasa como argumento ni se guarda. Si Supabase pide la contraseña de base, se ingresa en esa misma terminal. No copiar ninguna clave o frase al chat. Guardar la frase en un gestor de contraseñas personal: perderla impide restaurar. Si el proceso falla, el directorio queda **incompleto** (sin `COMPLETE.json`) y no sirve como respaldo de publicación.

Antes de aplicar migraciones:

- Elegir un destino fuera del repositorio y fuera de carpetas sincronizadas sin cifrado de extremo a extremo. El script cifra con una frase administrada por el titular. No subir dumps ni objetos a GitHub, Vercel o este chat.
- Comprobar que `COMPLETE.json` enumere los archivos de base y la cantidad de objetos. Conservar juntos los `.enc` y el manifiesto cifrado, y copiar el conjunto a un destino externo cifrado. Registrar fecha UTC, proyecto, último esquema, cantidad, tamaño y SHA-256 de los archivos cifrados, sin datos personales ni claves.
- Ensayar un descifrado y restore **en un proyecto aislado**, incluyendo la apertura de un original de Storage y una consulta de una cuenta de prueba. No restaurar sobre el proyecto vivo para ensayar. La mera existencia de los archivos no aprueba recuperación.
- Como comprobación local previa, ejecutar `node scripts/verify-backup-restore.mjs --source 'C:\Users\tavan\Documents\Codex\KusiyBackups\2026-09-27-before-e4-e13'`. Solicita la frase dos veces y verifica los ocho archivos. En un PostgreSQL temporal **sin red ni volúmenes**, restaura roles, esquema, datos propios de Kusiy, historial de migraciones y bytes de los objetos; al terminar elimina el contenedor. Omite las filas de Auth, los metadatos de Storage y las colas `pgmq` en esta prueba porque sus esquemas gestionados difieren del proyecto alojado. No modifica el respaldo ni Supabase remoto y no escribe originales en el host. **El titular ejecutó el ensayo sobre la copia cifrada completa: los cinco dumps restauraron, se recuperaron cuatro estados académicos y se verificaron dos archivos originales.** Como prueba complementaria, un dump reciente se restauró completo en un stack Supabase local separado: cuatro estados, siete usuarios Auth, dos metadatos Storage, diez migraciones y tres mensajes `pgmq`. Los dos originales se cargaron y leyeron mediante la API Storage local con SHA-256 idéntico. El stack y sus volúmenes se eliminaron. Esta segunda prueba verifica los servicios gestionados con datos actuales, pero no sustituye un restore integral de los mismos archivos cifrados ni una copia externa.
- Repetir antes de cada migración importante y después con periodicidad definida; conservar 30 días de copias externas según el Master Plan. La retención y acceso a datos de menores requieren revisión jurídica antes de usuarios reales.
